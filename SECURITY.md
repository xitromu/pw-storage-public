# Безопасность

## Как сообщить о проблеме

Приватный отчёт — через **Security Advisories** репозитория (GitHub → Security → Report a vulnerability).
Публичный issue только для того, что уже исправлено и не раскрывает способ обхода.

Что ускоряет разбор: версия (`git rev-parse --short HEAD`), профиль (`main` или `test`), шаг воспроизведения
и **вывод без значений**. Скриншоты с реальными именами строк тоже не нужны — достаточно комментариев.

Ожидай ответа в течение нескольких дней; срочность «секрет уже утекает» пиши прямо в заголовке.

## Если секрет засветился

Порядок действий, от самого дешёвого:

1. **Отозвать доступ проекту**: `python pw.py close` (закрывает доступ всему проекту и снимает его ожидающие запросы).
2. **Закрыть посредника** — окно закрывается по `close` у владельца или завершением процесса; значения из памяти уходят.
3. **Выпустить новый секрет у провайдера** (токены, пароли сервисов) — это всегда внешняя система, программа её не переспит.
4. **Заменить значение в хранилище**: окно управления → запись → новое значение. Старое остаётся только в истории
   внешнего сервиса, в файлах проекта его нет.
5. **Сменить пароль хранилища**, если под подозрением он: окно управления → «Сменить пароль» (или
   `python -m pw_storage.admin passwd`).
6. **Перевыпустить часть ключа восстановления**, если есть основания полагать, что она скомпрометирована:
   `python -m pw_storage.admin reissue`.
7. Проверить журнал `logs/access.log`: кто и какую строку брал в злополучное окно времени.

Утечка **файла** хранилища (`vault.kdbx`, копия, снимок диска) — отдельный случай: пароль менялся бы и без
подозрений, но здесь его нужно сменить обязательно, потому что файл можно перебирать офлайн.

## Модель угроз: коротко

Защищает от:

- значений в файлах проектов, в git и его истории, в резервных копиях и в журналах;
- случайного вывода секрета в чат ассистента или в `stdout` — у клиента и `pw.py` нет команды печати значения;
- кражи файла хранилища или диска целиком (при стойком пароле: Argon2id 1 GiB, 4 итерации, 4 потока);
- автоматической выдачи «на всякий случай»: разрешение выдаёт человек, на выбранные строки и на срок.

Не защищает от:

- процесса, запущенного от твоей учётной записи, пока хранилище открыто посредником: у него есть канал и права;
- намеренного обхода правил ассистентом или скриптом (фильтр по проекту — от ошибки, не от злого умысла);
- клавиатурного шпиона, модифицированного кода в `.venv`, вредоноса с правами администратора или ядра;
- кражи уже расшифрованного значения из памяти процесса-получателя;
- слабости самого пароля: KDF тормозит перебор, но не делает короткий пароль стойким.

Подробности и таблица «атака → что мешает» — [docs/security-model.md](docs/security-model.md).

## Правила, которые держит код

- Журнал доступа (`logs/access.log`) содержит имена, номера строк, проекты и события. Значений там не бывает;
  тесты проверяют, что ни одно сообщение не содержит полученный секрет.
- Пароль хранилища и код доступа через бота вводятся только со скрытым полем и не пишутся в файлы.
- Часть ключа восстановления показывается один раз при создании или перевыпуске и не сохраняется на диске.
- Сообщение с кодом доступа бот удаляет; неверные коды ограничены тремя попытками на запрос (TPM ведёт свой счёт).
- Архив выгружается только на носитель, помеченный доверенным по серийному номеру, том с Windows отвергается;
  пароль архива — не короче 20 знаков, шифрование AES-256.
- Строки без комментария не выдаются: «что это» должно быть видно владельцу до решения.
- Перечень строк (`catalog.bin`) запечатан ключом TPM этого ПК и не читается с другого компьютера.

## Зависимости

`requirements.txt` зафиксирован с хешами (`uv pip compile --generate-hashes --only-binary :all:`), установка идёт
с `--require-hashes`: другой сборки или изменённого пакета pip не поставит. Обновление — осознанный шаг:

```bat
uv pip compile requirements.in --generate-hashes --only-binary :all: --python .venv\Scripts\python.exe -o requirements.txt
```

Свои библиотеки поверх ядра не нужны: интерфейс клиента стабилен, а сторонний код в том же `.venv` имеет
доступ к открытому хранилищу на правах твоей учётной записи.

## Чего программа не делает

Не отправляет ничего наружу, кроме явных операций: подтверждение через твой Telegram-бот (токен и chat id лежат
в записях хранилища) и запросы `getUpdates`/`sendMessage` к API Telegram. Телеметрии, обновлений из сети,
облачной синхронизации и сторонних серверов в коде нет.
